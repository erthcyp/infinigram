How I investigated infini-gram

The assignmentWhat I was actually asked

HalluTrace decides where a hallucination came from by searching the model's own pretraining corpus twice. Once for the erroneous thing the model said, once for the correct thing it should have said. Two numbers come back, and those two numbers decide everything. 

c_true  = how often the correct form appears
c_false = how often the erroneous form appears

correct present, erroneous absent    the data was fine, the model forgot
erroneous present, correct absent    the mistake was in the data
neither present                      nothing was ever there
both present                         the corpus disagreed with itself

From those labels we derive the intervention point, the remedy we recommend, and the cross tabulation that is the paper's headline. The entire project sits on two integers.

So my job was narrow and important. Before anyone writes a pipeline, find out what those integers actually mean. When you ask infini-gram how many times a string occurs in a corpus, what is it really counting?

I expected to spend an afternoon confirming that it counts what it says it counts, and to report back that we were fine. That is not what happened.

Step oneTen minutes in a browser

There is no tutorial for this tool. No video, no course, no blog post walking through it. There is a paper, an API document, and a web interface where you pick a corpus, type a string, and press a button. I started there, because it costs nothing.

First I needed to understand what I was querying. infini-gram takes a corpus, concatenates it into one long array of tokens, and builds a suffix array over it: every starting position, sorted by the text that follows. Because the list is sorted, all the places beginning with a given phrase sit next to each other in one block. Counting is two binary searches and a subtraction.

That design has a consequence I did not appreciate until later. Nothing is precomputed per phrase length, so the phrase can be any length at all. And the index is built over tokens, not over characters and not over words.

Step twoThe first crack

Zero. Clean result, easy label, and I nearly moved on. Then I looked at the second column, which the interface shows underneath the answer and which I had been ignoring. 

pd.read_json    [10518, 29889, 949, 29918, 3126]
pd.read_jsonl   [10518, 29889, 949, 29918, 3126, 29880]
                 ^^^^^^ identical prefix ^^^^^^   plus one

The erroneous form is not a different sequence. It is the correct form with a single token stuck on the end. And infini-gram counts occurrences of a token sequence, wherever they occur.

What that means

Every occurrence of pd.read_jsonl in the corpus would be counted inside the number for pd.read_json. Silently. The 35,040 would include them, and nothing in the response would say so.

In this particular case nothing is lost, because the longer form has count zero. But that is luck, not safety. The mechanism is structural, and it applies to every pair where the wrong form extends the right one.

I sat with the failure direction for a while, because it is the worst possible one. Contamination inflates c_true. Inflating c_true pushes a claim out of the mistake was in the data and into the data was fine. Our system would tell a team to stop looking at their corpus at exactly the moment the corpus is the problem.

Step threeThe obvious fix, and why it collapsed

The fix seemed easy. Anchor the query. Append a character that cannot be part of a function name, so nothing longer can hide inside it. For a Python call, an opening parenthesis.

pd.read_json35,040100%
pd.read_json(21,43261.2%
unaccounted for13,60838.8%

Anchoring threw away thirty nine percent. And I already knew none of it was the longer identifier, because that has count zero. So thirteen thousand legitimate occurrences had vanished and I did not know where they went.

My first guess was that they were other kinds of boundary. A space, a newline, a comma. That guess was wrong, and finding out why was the most useful thing I did all week.

Step fourAsking a different question

Instead of guessing what follows the string, I asked. The interface has a tab that computes the distribution over the next token: given this phrase, what comes after it in the corpus, and how often.

Look at the three rows in red. They are all opening parentheses.

This is the whole finding

Byte pair encoding merged the parenthesis with whatever followed it. (' is one token. (" is one token. ('/ is one token.

My anchored query asked for the token ( on its own. So it never matched pd.read_json('data.json'), because in that text the tokenizer never produced a bare parenthesis. It produced ('.

The thirty nine percent I lost was not a different kind of boundary. It was the same parenthesis, tokenized differently because of the character after it.

Which kills the approach entirely. Under byte pair encoding, text that looks identical to a person tokenizes differently depending on its neighbours, and there is no way to enumerate in advance what to append. Anchoring on a character is not a conservative fix. It is a silent undercount whose size you cannot predict.

The distribution, though, does not require me to guess anything. It reports what is actually there. That felt like the answer, so I checked whether I could trust it.

Step fiveThe catch

The response carries a flag called approx. For plain counts it comes back false. For the next token distribution it comes back true, and I wanted to know how much that mattered.

I had two numbers I could check it against, because I had already measured them directly.

ContinuationDistributionExact countError
pd.read_json + (21,47521,4320.2%
pd.read_ + json32,76835,0406.5%

The error grows with volume. And then I noticed the numbers themselves.

32,768 = 2^15        24,576 = 3 x 2^13
16,384 = 2^14         6,144 = 3 x 2^11
 4,096 = 2^12         2,048 = 2^11

Powers of two, over and over. The service samples continuations and scales the sample back up, so the individual figures are quantized estimates. The total is exact, which is why all eighteen rows sum to precisely 35,040 while single rows are off by thousands.

What I took from that

Use the distribution to learn which tokens follow. Never use it to learn how many. The identity of a token is reliable even when the number attached to it is not, and identity is the only thing I need from it.

Step sixThe procedure

Two query types, each used for the one thing it is good at. What comes out has no approximation left in it anywhere.

  • Count the string. Exact, but may include longer strings that extend it.
  • Ask what follows. Returns every token that appears next. Ignore the numbers.
  • Classify each one. A token continues the identifier when its first character is a letter, a digit or an underscore, with no leading space marker. Everything else is a boundary.
  • Count each continuation exactly. One count query per continuing token. Exact again.
  • Subtract. Raw minus the sum of those exact counts.
def continues(token):
    if not token:
        return False
    first = token[0]
    if first in ("▁", " "):          # sentencepiece space marker
        return False
    return first.isalnum() or first == "_"


def clean_count(s, index):
    raw = count(s, index)                        # exact
    if raw == 0:
        return 0
    nxt = next_token_distribution(s, index)      # identities only
    bad = [t for t in nxt if continues(t)]
    return raw - sum(count(s + t, index) for t in bad)   # exact

Most strings have nothing continuing them, so the normal case costs two queries instead of one. Our projected ninety thousand queries becomes roughly one hundred and eighty thousand, which at the latencies I measured is under three hours in total. The schedule does not move.

Step eightThe case that would have changed our answer

Everything up to here establishes a mechanism. This is the one where I watched it change a conclusion we would otherwise have published.

The consequence, stated plainly

Our decision rule turns on whether that ratio reaches 0.5. Raw counts put it at 0.779, which means clean the corpus. Clean counts put it at 0.274, which means the corpus is not at fault and the problem lies in training or in decoding.

Different team, different budget, opposite recommendation. The answer flipped from one end of our framework to the other, purely because of how tokens were counted.

Step nineOne more question while I was in there

A separate question, unrelated to tokenization, that I could answer cheaply since the machinery was already running.

Work that traces hallucinations back to training data usually cannot search the real corpus, because most models do not publish theirs. HALoGEN, the closest prior work to ours, searched Dolma for OLMo but substituted C4 for Llama and OpenWebText for the GPT models, and named this in its limitations. Nobody has measured what the substitution costs. I ran the same four pairs against C4 to find out.

C4 is thirteen times smaller than Dolma by tokens, but these counts fall by between 779 and 8,760 times. That gap is not about size. C4 is filtered web text with almost no source code in it, while Dolma contains code repositories and developer forums. At counts of 4 and 7, one document would change the answer.

How far I am willing to push this

Not very. All four pairs are Python API names, which is precisely where C4 is weakest. For claims about people or papers the gap would probably be narrower. Four items is a preview, not a result. The real control needs a sample balanced across all three of our tasks, and that belongs in the paper rather than here.

ConclusionsWhat I believe now

  • Token boundary contamination is real and structural, not a corner case. It follows from how the index is built.
  • Anchoring on a character is unsound under byte pair encoding. It lost 39 percent in the one case I measured, and the size of the loss is unpredictable.
  • The next token distribution is approximate, by up to 6.5 percent, with a quantization signature visible in the raw numbers.
  • Identify with the distribution, measure with exact counts. The result carries no approximation.
  • The rule behaves correctly at both extremes, zero and one hundred percent contamination.
  • Throughput is not a risk. Every query I ran returned in 10 to 50 milliseconds.
  • The correction changes conclusions, not just numbers. One case in four moved across our decision threshold.
Why this is worth a section in the paper

HALoGEN searched training data with WIMBD, which matches documents and text rather than tokens, so it never met this problem and had no reason to describe a solution. Later work using infini-gram has not applied it to hallucination provenance. There is no precedent for us to follow here, which means the procedure above is something we contribute rather than a footnote about tooling.

Honest gapsWhat I could not settle

  • How often cleaning changes a label. One in four here, on four items, all code. This has to become a measured figure across all three tasks.
  • Whether the rule holds outside code. Person names, paper titles and venue names tokenize differently from function names. Untested.
  • Case and whitespace. The API is case sensitive, and a leading space changes the tokenization completely. Our query forms must be fixed and identical across all five corpora before generation starts, and I have not written that specification yet.
  • The browser truncates. The web interface shows the top ten continuations only. Read the full response through the API, or a rare continuation will hide in the tail where nobody looks.
  • OLMo 3 indexes now exist at 6.1T tokens, which I did not expect to find. But each query against them takes 12 to 15 seconds and they do not support boolean queries, roughly three hundred times slower than what we use. Future work, not this paper.

ReproduceRun it yourself

Standard library only. No installation, no key. Ten minutes end to end.

import json, urllib.request, time

URL = "https://api.infini-gram.io/"

def call(index, **body):
    body["index"] = index
    req = urllib.request.Request(
        URL, data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"})
    for attempt in range(4):
        try:
            with urllib.request.urlopen(req, timeout=60) as r:
                return json.loads(r.read().decode())
        except Exception:
            if attempt == 3:
                raise
            time.sleep(1.5 * (attempt + 1))

def continues(tok):
    if not tok:
        return False
    ch = tok[0]
    if ch in ("▁", " "):
        return False
    return ch.isalnum() or ch == "_"

def clean_count(s, index):
    raw = call(index, query_type="count", query=s).get("count", 0)
    if raw == 0:
        return 0, 0, []
    d = call(index, query_type="ntd", query=s)
    bad = [v.get("token") for v in d.get("result_by_token_id", {}).values()
           if isinstance(v, dict) and continues(v.get("token"))]
    subtracted = sum(
        call(index, query_type="count", query=s + t).get("count", 0)
        for t in bad)
    return raw - subtracted, raw, bad

def label(t, f):
    if t > 0 and f == 0:  return "CORRECT_IN_DATA"
    if t == 0 and f > 0:  return "WRONG_IN_DATA"
    if t == 0 and f == 0: return "NOT_IN_DATA"
    return "MIXED"

INDEX = "v4_dolma-v1_7_llama"
PAIRS = [
    ("pd.read_json",                        "pd.read_jsonl"),
    ("from sklearn.model_selection import", "from sklearn.cross_validation import"),
    ("pandas.plotting",                     "pandas.tools.plotting"),
    ("np.float64",                          "np.float"),
]

for good, bad in PAIRS:
    ct, _, _ = clean_count(good, INDEX)
    cf, _, _ = clean_count(bad, INDEX)
    r = cf / (ct + cf) if (ct + cf) else 0
    print(good, ct, "|", bad, cf, "|", label(ct, cf), round(r, 4))

Swap INDEX for v4_c4train_llama, v4_dclm-baseline_llama, v4_piletrain_llama or v4_rpj_llama_s4 to repeat the corpus comparison.
